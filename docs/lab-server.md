# 可控 MCP 实验服务器（lab）

更新：2026-11-20。状态：服务器、判定器和评测流程在 2026-11-20 做过一轮大改（见"2026-11-20 的改动"）。改动之后只做了不调用模型的机制检查，**还没有用真实模型重跑**；本文和其他文档里出现的真实模型数字都是改动之前的。

现有三个公开数据集的环境是隔离的：没有外部变化，不支持幂等键，目录不变，会话不会被服务端作废。调度器里好几项机制在上面起不了作用。lab 服务器是为了补上这些条件而搭的：一个小的模拟服务世界，凡是缓存和恢复策略可能出错的地方，都是任务里可以控制的输入。

## 怎么用

```bash
./run lab-check --suite all --server
```

不调用模型的机制检查，几十秒。它把每个任务的参考解法分别套上九种方法在进程内回放，再通过真实的 MCP 服务器和正式的 runner 跑一遍，核对两条路径是否一致。常用选项：

| 选项 | 含义 |
|---|---|
| `--suite basic` / `stress` / `all` / `heldout` | 基础 10 条、极端场景 30 条、两者合计、留出集 24 条 |
| `--listing per_turn` / `per_connection` | 代理框架多久向 Host 要一次工具清单 |
| `--contract full` / `annotations` / `none` / `wrong` | Host 能拿到多少工具契约 |
| `--why` | 打印每个失败运行没通过的判定项 |

用真实模型评测（`--shadow-verify` 打开交付审计，`--repeats` 做重复运行）：

```bash
./run smoke --manifest data/lab-stress-cases.json --methods bare strong ours --scheduler default --shadow-verify --repeats 3 --results-root results/某次运行
./run lab-report --root results/某次运行
```

其他命令：`./run lab-rejudge --root 目录`（用当前判定器离线重判已有运行）、`./run adapt --trace-root 目录`（从一次运行的记录自动定参，见 [adapt.md](adapt.md)）。

## 服务世界

三个应用挂在同一个 MCP 服务器后面，共 17 个工具，另有 2 个（批量价格、报价）只在目录更新后出现。

| 应用 | 工具 | 需要登录 |
|---|---|---|
| 银行 `bank` | 列出账户、查余额、查转账记录、转账 | 是 |
| 商店 `shop` | 列出商品、查商品信息、查价格、查库存、下单、列出订单、取消订单 | 是 |
| 公共数据 `ref`、时钟 `clock` | 列出币种、查汇率、当前时间 | 否 |
| 通用 | 登录、登出、按操作键查询某次写的结果 | — |

**时间是虚拟的。** 服务器有自己的时钟：代理每走一个决策步过 10 秒，任务可以设定两轮对话之间的间隔。Host 的所有过期判断都读这个时钟，不读真实时间，所以结果不随模型回答的快慢变化。

**登录是令牌。** 登录返回一个令牌，Host 之后的每个请求都带着它。服务器检查令牌属于谁、是否被作废、是否按虚拟时钟到期。携带令牌属于传输层，对所有方法相同。

**操作键。** 写操作可以带一个操作键。服务器记下见过的每个键、它对应的请求和发送者：
- 支持幂等键的工具（转账），同一个键重发只返回原结果。
- 同一个键配了不同的请求会被拒绝。
- 查询某个键的结果：已执行、未执行，或者"不知道"（服务器没见过这个键）。查询要以发送者的身份登录。

## 可以控制什么

| 可控因素 | 怎么控制 |
|---|---|
| 外部变化 | 改价格、改库存、存入一笔钱 |
| 会话作废 | 服务端作废某个应用的全部登录 |
| 登录有效期 | 任务设定令牌的寿命，按虚拟时钟到期 |
| 目录变化 | 新增、下线工具，改描述，改版本号，也可以不改版本号悄悄变；工具返回的含义可以变 |
| 目录的大小和可见性 | 填充无关工具；目录随登录状态变化 |
| 故障 | 某个工具的第 n 次调用：限流、暂时不可用、回复丢失（已生效）、请求丢失（未生效） |
| 延迟 | 全局延迟加抖动；单个工具的额外延迟 |

外部变化、会话作废和目录变化可以挂在三种时刻：
- 某一轮对话开始时；
- 代理对某个工具的第 n 次调用完成之后（同一轮之内）。这里数的是代理发起的调用，不管它是不是被 Host 的缓存挡下了，所以对所有方法在任务的同一个位置触发；
- 虚拟时钟走到某一秒时。

"请求丢失"和"回复丢失"对 Host 来说现象完全相同，都是没有回复。任务文件在加载时校验：不可能生效的故障或事件配置会直接报错。

## 服务器公布的契约

每个工具带一份契约：是读、写、登录还是登出；读取结果的新鲜度级别（不变、慢变、易变、严格）；读取依赖哪些资源、写操作影响哪些资源；属于哪个账号；是否支持幂等键。

有一项测试核对契约：执行写操作，凡是结果发生变化的读取，都必须落在这次写声明的影响范围内。这项测试只覆盖预先列出的 4 个写操作和约 20 个读取，不是穷举。

## 对所有方法相同的实验因素

**列目录的频率。** 代理框架多久向 Host 要一次工具清单，是 runner 决定的，不是模型的行为。`per_turn` 是每轮对话开始时要一次，`per_connection` 是整个任务只要一次；两种情况下服务器宣布目录变化时都会再要一次。目录请求在结果里单独计数，报告时和其他请求分开。

**契约等级。** Host 能拿到多少契约，对所有方法一样：

| 等级 | Host 拿到什么 |
|---|---|
| `full` | 完整契约 |
| `annotations` | 只有协议注解能表达的：是读还是写。没有新鲜度级别、资源和幂等键信息 |
| `none` | 什么都没有，每个工具都可能改状态，所以没有可缓存的读取 |
| `wrong` | 完整契约里放两处服务器真可能犯的错：转账漏报了它会改目标账户的余额；价格被标成慢变 |

**交付审计。** 打开后，每个交给代理的读取结果都会和服务器此刻的真实值比对一次（不计入请求数）。对无缓存、旧缓存、调度器用的是同一套检查。分开统计：交付了过时的值；会话已失效仍然交付；检查本身失败。新调度器向模型提供的"仍然有效"的引用是另一条交付通道，同样审计。

## 方法

机制检查里有九列：

| 列 | 是什么 |
|---|---|
| 无缓存 | 不复用任何状态 |
| OpenAI 适配、FastMCP 适配、Gateway 启发、Mehan 启发、固定组合 | 五个诊断性的对照组合。它们是局部适配，不是原工作的忠实复现，也拿不到契约里的资源信息和操作键 |
| 旧版 Ours | 旧原型 |
| 强基线 `strong` | 与本文方法能力相同：同样的契约、操作键、状态查询、自动重新登录。但只用固定的常规规则：慢变类 60 秒过期、易变类不缓存、任何写操作让整个应用的读取失效、不向模型提供额外状态 |
| 新调度器 | 本文方法，默认参数 |

强基线和新调度器的差别只在调度策略，不在能力。要回答"收益来自能力还是来自策略"，看这两列。

## 判定器

代码在 [exp_core/lab/judge.py](../exp_core/lab/judge.py)。按可靠程度从高到低检查四类证据：

1. **最终状态**：全部账户余额、商品价格和库存、订单、运行期间产生的转账，整体与参考结果比对。
2. **写操作**：实际生效的写操作连同完整参数，与参考结果逐条比对。
3. **代理拿到的结果**：在检验泄露的那些轮次，看 Host 实际交给代理的内容。"必须被拒绝"的规则要求代理确实尝试过；没有尝试不算通过。
4. **回答**：数值按数值比较（"1,200"等于 1200，"500.99"和"-500"不等于 500，编号里的数字不算数值），并且要出现在它所属的对象旁边。

参考结果从每个任务的参考解法自动导出（[data/lab_expect.py](../data/lab_expect.py)）：在无缓存、去掉注入故障的条件下跑一遍，得到最终状态、写操作清单和每个数值所属的对象。

每项检查有三种结果：通过、失败、待复核。整次运行的结论相应是通过、失败或待复核，待复核不计入通过。

**安全和完成分开判。** 除了是否通过，每次运行还有一个"是否安全"：生效的写操作里有没有参考结果之外的（重复的、金额不对的）。停下来如实报告而没完成任务，是安全但未通过；把转账执行了两次是不安全。

服务器同时记录每个写请求的结局（已提交、被拒绝及原因、按键重放、到达前丢失、提交后回复丢失），以及每个预定故障是否真的命中。

已知的不足：
- 回答里正确值和错误值同时出现时，只要正确值挨着对象就算通过。
- "回答是否如实说明成功或失败"只有一条粗略的关键词规则，命中后转人工复核。
- 对象名取自参考回答里的一个词，模型换一种叫法会被标成待复核。

## 任务

| 文件 | 内容 | 用途 |
|---|---|---|
| `data/lab-cases.json` | 基础 10 条，六类场景 | 开发 |
| `data/lab-stress-cases.json` | 极端场景 30 条：目录、读取、凭据、操作状态、时间点、复合，各 5 条。见 [lab-stress-cases.md](lab-stress-cases.md) | 开发 |
| `data/lab-heldout-cases.json` | 留出集 24 条 | 只用于最终评测 |

**留出集**由 [data/lab_heldout.py](../data/lab_heldout.py) 按固定种子生成：8 种场景结构，每种 3 个实例，账户、金额、商品、轮数、每次扰动的时刻和种类都由随机数决定。答案里要出现的数值也不是手写的，是从参考解法读出来的。生成后冻结：锁文件 `data/lab-heldout.lock.json` 记着任务文件的哈希，测试会核对，也会核对重新生成得到完全相同的内容。

留出集的局限要说清楚：
- 生成器是在知道各方法实现的情况下写的。
- 默认参数在生成之前已经在开发 case 上选定。
- 冻结之后，机制检查的结果已经看过，并且之后改过一次默认参数（易变类有效期从 4 步改为 0）和一处缺陷（凭据到期后仍返回缓存）。留出集上新调度器的数字因此从 22 条、323 次变成 24 条、340 次。也就是说，对当前的默认参数，这批留出集已经不是没看过的数据了。要得到干净的留出结果，需要换一个种子重新生成一批，并且在生成之后不再改参数。

## 机制检查结果

执行任务的是照剧本走的脚本代理，不是模型。这些数字说明机制是否正确，不说明真实模型的表现。每格是 40 条开发 case 或 24 条留出 case 的合计。列的顺序同上。

**开发集（40 条），完整契约，每轮列一次目录：**

| | 无缓存 | OpenAI | FastMCP | Gateway | Mehan | 固定组合 | 旧版 Ours | 强基线 | 新调度器 |
|---|---|---|---|---|---|---|---|---|---|
| 通过 | 39 | 38 | 12 | 28 | 39 | 28 | 28 | 37 | 37 |
| 请求数 | 611 | 530 | 607 | 447 | 611 | 447 | 447 | 443 | 411 |
| 其中列目录 | 149 | 69 | 149 | 70 | 149 | 70 | 70 | 65 | 65 |
| 交付了过时的值 | 0 | 0 | 56 | 14 | 0 | 14 | 14 | 5 | 6 |
| 会话失效后仍交付 | 0 | 0 | 33 | 3 | 0 | 3 | 3 | 3 | 6 |
| 有不安全写的运行 | 1 | 1 | 5 | 4 | 1 | 4 | 4 | 0 | 0 |

**留出集（24 条），同样条件：**

| | 无缓存 | OpenAI | FastMCP | Gateway | Mehan | 固定组合 | 旧版 Ours | 强基线 | 新调度器 |
|---|---|---|---|---|---|---|---|---|---|
| 通过 | 24 | 24 | 1 | 17 | 24 | 17 | 17 | 24 | 24 |
| 请求数 | 441 | 378 | 457 | 323 | 441 | 323 | 323 | 360 | 340 |
| 其中列目录 | 100 | 37 | 100 | 37 | 100 | 37 | 37 | 33 | 33 |
| 交付了过时的值 | 0 | 0 | 93 | 17 | 0 | 17 | 17 | 0 | 0 |
| 有不安全写的运行 | 0 | 0 | 4 | 1 | 0 | 1 | 1 | 0 | 0 |

两个集合上，真实 MCP 服务器的运行与进程内回放在"是否通过、请求数、目录请求数、过时交付的清单"四项上全部相同。

怎么读：

- **新调度器和强基线在正确性上相同**：开发集都是 37 条，留出集都是 24 条，两者没过的是同样三条，都是契约漂移的对抗场景（契约说余额只随自己的写变化，实际有外部存款）。
- **新调度器的请求数更少**：开发集比强基线少 7%，留出集少 6%。这部分才是调度策略（按资源失效等）带来的。
- **默认参数在看过留出集结果之后改过一次**，必须说明：易变类的默认有效期原来是 4 步，会把易变数据复用几步，价格在同一轮里被改时用到旧值。这个问题先在开发集的 `time-midturn-price-change` 上发现，留出集的两条价格 case 上也出现了（当时新调度器在留出集上是 22 条、326 次请求）。之后默认值改成 0（易变数据不缓存），留出集变成 24 条、340 次。所以留出集上"24 条全过"不是一个事先冻结参数得到的结果。
- **无缓存在开发集没过的 1 条**是 `lab-fault-lost-ack`：它的参考解法故意是"出错就重发"，无缓存因此把转账执行了两次。其他会话恢复类 case 的参考解法都是先查状态再决定。
- **能力带来的差别很大**：从固定组合到强基线，通过数 28 到 37。此前"新调度器比旧方法多通过若干条"的说法，大部分应归于能力（契约和操作键），而不是调度策略。

**换一种列目录频率（开发集，整个任务只列一次）：**

| | 无缓存 | 强基线 | 新调度器 |
|---|---|---|---|
| 通过 | 38 | 34 | 34 |
| 请求数 | 518 | 432 | 400 |
| 其中列目录 | 57 | 57 | 57 |
| 其余请求 | 461 | 375 | 343 |

每轮列一次时，新调度器比无缓存少 200 次请求，其中 84 次是目录。只列一次时目录缓存没有任何收益，差距是 118 次（23%），全部来自其他请求。所以"请求数少多少"必须注明列目录的频率，并把目录和其余请求分开报告。通过数下降是因为悄悄发生的目录变化在只列一次时谁也发现不了。

**换一种契约等级（开发集，每轮列一次目录）：**

| 契约等级 | 强基线：通过 / 请求 / 过时交付 | 新调度器：通过 / 请求 / 过时交付 |
|---|---|---|
| 完整 | 37 / 443 / 5 | 37 / 411 / 6 |
| 只有读写注解 | 29 / 430 / 13 | 29 / 390 / 17 |
| 没有契约 | 39 / 517 / 0 | 39 / 516 / 0 |
| 契约有两处错误 | 31 / 431 / 12 | 28 / 373 / 32 |

- 没有契约时，两者都退化成只缓存目录，结果和无缓存一样正确。
- 只有读写注解时，两者都会把易变数据当普通读取缓存，通过数掉到 29。在有外部变化的环境里，只凭"这是读操作"来缓存是不安全的。
- 契约有错时，新调度器受的影响更大（过时交付 32 对 12），因为它更细地信任契约。交付审计能把这类错误量出来。

## 2026-11-20 的改动

起因是一轮评审（[lab-server-review.md](lab-server-review.md)），列出 11 项必须改的问题。对应的改动：

| 评审的问题 | 改动 |
|---|---|
| 判定器会把错的判对 | 重写判定器；已有运行可离线重判 |
| 外部变化只发生在轮次开头；没有统一时钟 | 虚拟时钟；事件可挂在某次调用之后或某个时刻；新增 5 条时间点 case |
| 契约和服务能力只接给了新调度器 | 强基线；契约等级做成所有方法共用的因素 |
| 每轮固定列一次目录 | 列目录频率做成因素；目录请求单独计数 |
| 操作键语义有错 | 未知的键返回"不知道"；键绑定请求和发送者；状态查询要登录 |
| 过时和越权没有统一度量 | 交付审计，对所有方法相同 |
| 开发和确认用同一批 case；只跑一次 | 留出集 24 条；`--repeats` 和 `./run lab-report` |
| 操作状态只有一条最容易的 case | 新增 5 条：请求丢失、不支持幂等键的写、状态查询不可用、连续故障、结果未知时会话作废；安全和完成分开判 |
| 凭据只测了省掉多余登录 | 令牌随请求携带，按虚拟时钟到期，可被作废 |
| 故障计数在授权之前；配置不校验 | 计数移到授权之后；任务文件加载时校验；记录故障是否命中 |
| 文档与代码不符 | 本文重写；极端场景文档更新 |

新 case 还查出调度器本身的四个问题，都已修正：

1. **结果未知的写被说成"未执行"。** 转账的回复丢失后，Host 带同一个键重发，这次重发因为会话刚被作废而被拒绝，Host 就把"未授权"交给了代理。代理据此重新登录并重发，转账执行了两次。现在只要有一次尝试结果未知，后续尝试被拒绝也不会改变结论，交给代理的是"结果未知"。
2. **记住的业务失败一直被复用。** 下单因为没货被拒之后，同样的下单请求不再发给服务器，即使后来补了货。现在这类记录有自己的有效期，默认 4 步（`recovery.failure_ages`、`recovery.failure_ttl`）。
3. **写被拒绝后，相关的缓存读取仍被当作当前值。** 现在写操作被业务原因拒绝时，它声明会影响的资源上的缓存读取一并失效（`invalidation.on_refused_write`）。
4. **凭据到期后仍返回在它名下读到的缓存。** Host 自己知道凭据什么时候到期。现在到期时会让这个账号名下的缓存失效。

## 仍然存在的边界

- lab 的工具是通过适配服务器的 `invoke` 包装后提供的，工具定义写在提示里交给模型，不是注册成 MCP 原生工具；目录走的是自定义工具而不是协议的 `tools/list`，没有分页。
- 目录变更通知由每个决策步之前的控制调用带回，相当于"每一步之前可靠送达"的最好情况。通知迟到、丢失的情形没有测。
- 登录是带内工具，不是 HTTP 层的 OAuth。
- 服务端作废会话后，Host 在下一次回源之前并不知情，这期间缓存的读取仍会被交付。协议里没有撤销通知，Host 侧修不了，交付审计把它单独统计。
- 单进程、单世界、单代理、顺序调用，没有并发和多会话。
- 没有容量压力的 case；延迟的档位没有系统地做。
- 真实服务器与回放的一致性核对比较四项，不逐次比较返回值。
