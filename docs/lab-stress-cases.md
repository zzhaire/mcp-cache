# 极端场景与复合场景 case（共 30 条）

更新：2026-11-20。状态：30 条都通过了不调用模型的机制检查。其中后加的 10 条（时间点、操作状态）和 2026-11-20 改动之后的服务器**还没有用真实模型跑过**；文中的真实模型结果是改动之前在最早的 20 条上得到的。

目的：在可控的 [lab 服务器](lab-server.md)上，为目录、读取结果、凭据、操作状态、外部变化的时间点各构造一个极端场景，再加一个多种因素同时出现的复合场景，每个场景 5 条。全部是开发材料；最终评测另有冻结的留出集，见 [lab-server.md](lab-server.md) 的"任务"一节。

## 怎么用

不调用模型的机制检查（几秒钟）：

```bash
./run lab-check --suite stress --why
```

`--why` 会打印每个失败运行没通过的判定项。加 `--server` 会再通过真实的 MCP 服务器跑一遍并核对。

用真实模型评测：

```bash
./run smoke --manifest data/lab-stress-cases.json --methods bare ours --scheduler default
```

case 由 [data/lab_stress.py](../data/lab_stress.py) 生成。要改 case 就改这个脚本，然后重新生成：

```bash
python -m data.lab_stress
```

## 设计思路

"极端"的意思是把一个模块逼到它最容易出问题或收益最大的地方。每个场景的 5 条从不同方向下手，尽量不重复：

- 有的是**收益极端**：重复次数很多，缓存应该省掉绝大部分请求。
- 有的是**正确性极端**：用了过时的状态就会答错、下错单，或者把数据给了不该给的人。
- 有的是**无收益极端**：一切都在变，缓存省不了什么，但也不能因此出错或多花请求。

每条 case 都有多轮用户指令（3 到 8 轮）、一份参考解法和一个判定器。判定器的说明见 [lab-server.md](lab-server.md) 的"判定器"一节。

## M1：目录

| case | 极端之处 | 要考验的点 |
|---|---|---|
| `m1-relist-large-stable` | 77 个工具的目录（约 25 KB），8 个 turn 每次都要列，目录始终不变 | 目录缓存的收益上限 |
| `m1-version-churn` | 目录每个 turn 都升版本，新增的工具马上要用 | 缓存不能把变化挡在外面 |
| `m1-silent-semantic-change` | 服务器声明有效期为 0；某个工具的返回含义变了，版本号不变，也没有通知 | 遵守服务器给的有效期，靠内容比对发现变化，并让该工具的旧结果失效 |
| `m1-notification-noise` | 每个 turn 都发变更通知、版本号加一，内容其实没变 | 要重新确认目录，但不该丢掉无关的读取结果 |
| `m1-tool-retired` | 旧工具被悄悄下线、换成新工具，版本号不变 | 拿着旧目录既看不到新工具，又会去调用不存在的工具 |

## M2：读取结果

| case | 极端之处 | 要考验的点 |
|---|---|---|
| `m2-read-storm` | 6 个 turn 都要同样的 6 项只读信息，没有任何变化 | 读取缓存的收益上限 |
| `m2-write-interleave` | 4 次转账涉及不同的账户对，每次之后重读全部 4 个余额 | 每次写只应让受影响的两个账户失效 |
| `m2-volatile-churn` | 价格和库存每个 turn 都被外部改动，要按最新值决定下不下单、下哪一个 | 用了任何一个旧值都会下错单 |
| `m2-contract-drift-repeated` | 契约说余额只随自己的写变化，实际每个 turn 都有外部存款 | **对抗性场景**：照契约缓存必然答错，只有回源校验能发现 |
| `m2-large-payloads` | 一份 150 条的记录（约 10 KB）和一份 600 条的记录（约 40 KB） | 大结果要能缓存并答对。超过单条上限的情形改在机制测试里覆盖（把上限调到 20 KB），因为真正超过默认上限 256 KB 的结果放不进模型上下文 |

## M3：凭据

| case | 极端之处 | 要考验的点 |
|---|---|---|
| `m3-relogin-storm` | 6 个 turn，每个 turn 开头都重新登录两个应用 | 凭据缓存能省掉多少次多余的登录 |
| `m3-session-churn` | 银行会话每个 turn 都被服务端作废，商店会话一直有效 | 自动重新登录；只丢银行一侧的缓存 |
| `m3-logout-must-not-serve` | 读完余额后主动登出，再读同一个余额 | 登出后必须被拒绝，不能返回登出前缓存的值 |
| `m3-user-switch` | 同一个应用里不登出、直接换成另一个用户 | 不能把上一个用户的数据带给下一个用户 |
| `m3-expiry-before-write` | 两次转账之前，会话都刚被作废 | 授权失败后的重试必须安全，转账只生效一次 |

## 复合场景

| case | 同时出现的因素 |
|---|---|
| `mix-office-day` | 47 个工具的目录、一次转账、一次按价格决定的下单、一次目录更新、一次外部调价、两个应用各一次会话作废、一次库存外部变化 |
| `mix-private-catalog-user-switch` | 目录随登录状态变化（登录了哪个应用才看得到它的工具），其间登录、换用户、登出交替发生 |
| `mix-everything-churns` | 每个 turn：目录版本号加一、价格被外部调高、至少一个会话被作废，并且要转一次账 |
| `mix-silent-change-under-load` | 两个工具的返回含义先后被悄悄改掉，其间有会话作废、一次转账和一次下单 |
| `mix-write-heavy-expiry-volatile` | 两次"先转出货款再下单"的连环操作，是否执行取决于当时的价格和库存；价格库存被外部改了三次，两个应用各被作废一次会话 |

## 时间点

外部变化不等到轮次开头才发生。这一组是评审之后加的：原先所有变化都挂在轮次开头，恰好落在新调度器清理易变数据之后，对它有利。

| case | 极端之处 | 要考验的点 |
|---|---|---|
| `time-midturn-price-change` | 同一轮里读两次价格，中间价格被外部调高 | 第二次读取必须是新的，否则会下错单 |
| `time-stock-gone-before-order` | 读到有 3 件货，下单前库存被清零，下单被拒 | 写被拒绝后，之前缓存的库存不能再当作当前值 |
| `time-midturn-contract-drift` | 契约说余额只随自己的写变化，同一轮里却来了一笔外部存款 | **对抗性场景**：照契约缓存必然答错 |
| `time-token-expires-mid-task` | 登录只有 60 秒有效，任务比这长 | 凭据按时间到期，到期后不能用旧凭据，也不能返回在它名下读到的缓存 |
| `time-think-time-between-turns` | 两轮之间隔 10 分钟；登录 15 分钟到期；价格在第 400 秒被调高 | 按真实时间流逝的过期 |

## M4：操作状态

写操作的结果 Host 看不到。参考解法是一个谨慎的代理：收到不明确的回复后先看状态，没生效才重发。

| case | 极端之处 | 要考验的点 |
|---|---|---|
| `m4-lost-request-and-lost-reply` | 一次转账的请求在途中丢失，另一次生效了但回复丢失 | Host 看到的现象相同，两种都要恰好生效一次 |
| `m4-order-without-idempotency` | 下单不支持幂等键，先后遇到回复丢失和请求丢失 | 没有幂等键时不能靠重发恢复 |
| `m4-status-query-unavailable` | 回复丢失，同时状态查询接口不可用 | 对账手段失效时不能把写当成未执行 |
| `m4-consecutive-faults` | 同一次转账连续遇到限流、不可用、回复丢失 | 多种故障叠加时重试必须安全 |
| `m4-unknown-then-session-dropped` | 回复丢失，紧接着会话被作废 | 结果未知的写不能因为授权变化被当成失败重发 |

怎么读这张表：

- **任务本身是可解的**：无缓存 30 条全部通过。
- **新调度器和强基线都没过 2 条**，是故意设的对抗场景（`m2-contract-drift-repeated`、`time-midturn-contract-drift`），契约本身不准。
- **易变数据默认不缓存。** 这是 `time-midturn-price-change` 这条 case 定下来的：原来的默认值把易变数据复用 4 步，价格在同一轮里被改时用到了旧值，下了一笔不该下的单。改成 0 之后这条通过，30 条合计只多 1 次请求。
- **新调度器比强基线少 8% 的请求**（357 对 387），差别主要在 M2：按资源失效比按应用失效省得多（46 对 62）。
- **旧的对照方法在这里按虚拟时钟计 60 秒有效期**，相当于 6 个决策步。此前它们按真实时间计，脚本代理跑得快，缓存几乎不过期，所以请求数比之前文档里的多。
- FastMCP 适配只过 7 条，原因是这个对照实现会缓存每一次成功的调用（包括登录和写操作）。它不代表配置得当的 FastMCP。

**这张表不能说明的事**：执行任务的是脚本代理；各对照方法是局部适配；30 条全部是开发材料，而且是在知道各方法实现的情况下设计的。

## 真实模型摸底结果（2026-11-19，改动之前）

模型：Claude Haiku 5.5，通过本机 `claude` 命令行调用。30 条（基础 10 条加极端场景 20 条），无缓存与新调度器（默认预设）各跑一次，打开陈旧命中统计。原始结果在 `results/lab-real-v3/`。

```bash
./run smoke --manifest data/lab-stress-cases.json --methods bare ours --scheduler default --shadow-verify --model claude-haiku-5-5 --workers 4 --results-root results/lab-real-v3
```

| 场景 | 无缓存：通过 / 请求数 | 新调度器：通过 / 请求数 |
|---|---|---|
| 基础 10 条 | 10 / 79 | 9 / 60 |
| M1 目录 | 5 / 49 | 5 / 42 |
| M2 读取 | 5 / 88 | 4 / 52 |
| M3 凭据 | 5 / 99 | 5 / 55 |
| 复合 | 5 / 139 | 5 / 118 |
| **合计** | **30 / 454** | **28 / 327** |

| 合计指标 | 无缓存 | 新调度器 |
|---|---|---|
| 模型调用次数 | 346 | 315 |
| 输入 token | 635 万 | 836 万 |
| 任务耗时合计 | 3151 秒 | 2849 秒 |
| 标价折算 | 1.11 美元 | 2.40 美元 |

怎么读：

- **新调度器没过的两条都是契约漂移**（`lab-contract-drift`、`m2-contract-drift-repeated`）：外部存款进来后仍返回缓存的旧余额。这是故意设的对抗场景，和机制检查的结论一致。陈旧命中统计在 30 次检查里记到 4 次过时，全部出在这两条上。
- **请求数少 28%**。差距最大的是 M3 凭据（99 对 55）和 M2 读取（88 对 52）。
- **输入 token 反而多了**，原因集中在 `m2-large-payloads` 一条：新调度器 364 万，无缓存 100 万。缓存命中让重复读取不再花请求，模型于是读得更多（20 次对 10 次），而每次命中仍把约 40 KB 的结果整份放进上下文。去掉这一条，新调度器的输入 token 是 472 万，无缓存是 535 万（少 12%）。结论是：对大结果，命中时应该只给引用而不是全文。
  - **已修正**（上表是修正之前的数字）：新增参数 `publish.large_repeat_min_bytes`，默认 4096。大结果只完整给模型一次，之后逐字节相同的结果只给一个指向那次调用的引用。修正后在这条 case 上跑了两次，输入 token 是 60 万和 55 万，都通过，模型调用从 15 次降到 10 次（结果在 `results/lab-large-repeat/`）。其余 29 条没有在修正后重跑。
- 每个配置只跑了一次，模型有随机性，单条 case 上的小差异不可信。

这轮评测之后改掉的问题（第一轮结果在 `results/lab-real/`，是改之前的）：

- 判定器把"回答里提到旧值"误判为泄露，6 次运行受影响。改为检查代理实际拿到的结果。
- 三条 case 的设计问题：`mix-everything-churns` 每轮指令一字不差，模型把后几轮当成重复请求；`mix-private-catalog-user-switch` 没给商店密码；`m2-large-payloads` 的 330 KB 结果放不进模型上下文。
- 模型有时把提示里的任务工具当成原生函数直接调用，原来会判整次运行失败。现在把这次请求按原意转成调用列表继续执行，token 全额计入，记录里留有标记。这轮 60 次运行里有 6 次发生过转换，共 10 次。

## 构造过程中发现并修正的问题

这 20 条 case 暴露了两个调度器接入层的真实缺陷，都已修正：

1. **登出之后，Host 又悄悄登录了回去**。Host 会记住登录信息，以便会话过期时自动重新登录。用户主动登出后这份记录没有清掉，于是下一次读取被拒绝时，Host 自动重新登录并返回了余额。现在登出会同时清掉这份记录。（`m3-logout-must-not-serve` 发现）
2. **同一个应用换用户时，上一个用户的缓存没有清**。缓存原来只按应用区分。alice 登录后读了余额，bob 不登出直接登录，再读同一个账户时拿到了 alice 的余额。现在检测到同一应用的登录用户变了，就让该应用的缓存全部失效。这条修正对所有方法生效，因为它在共用的接入层里。（`m3-user-switch` 发现）

另外有一处是脚本代理的问题，不是被测代码的问题：原来只有在我手写了恢复步骤的地方它才会重新登录，这让旧方法在几条复合 case 上因为剧本太死板而失败。现在"遇到未授权就重新登录并重试一次"是脚本代理的通用规则，只有明确要求"不登录看看会怎样"的那两个 turn 例外。

| 能力 | 用在哪里 |
|---|---|

## 已知的不足

- 判定器对回答里"必须出现的数值"仍然只做数值和关键词匹配，真实模型的回答需要抽查。
- 要求模型"如实报告服务的回答"的几个 turn（登出后读取、换用户后读取），只检查代理拿到的结果是否被拒绝，不要求回答里出现特定的错误字样。
- 还没有容量压力的 case：默认 4 MB 的总容量在这些任务里远远用不满。
- M4（操作状态）不在这次的范围内，只在几条 case 里顺带出现（授权失败后的写重试）。
