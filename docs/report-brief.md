# 进度报告（11 月 23 日）

## 一句话

我们在智能体和 MCP 服务器之间加了一层缓存。它稳定地让发到服务器的请求少三到六成。模型的开销要换一条新的发布规则才降得下来：在专门设计的三条 case 上，模型调用轮数少两到三成。这条新规则还不在设计稿里，实验规模也还很小。

## 做了什么

**1. 一层缓存。** 智能体每次调用工具都先经过它。它记四样东西：工具清单、查到的结果、登录凭证、每个操作办到哪一步。能用记下的就不再发请求。

关键在于什么时候不能再用旧结果：

- 自己改过的作废，没碰过的留着。转账后只作废这两个账户的余额。
- 不知道改了什么，就把整个应用的结果都作废。
- 价格、库存这类别人随时会改的，不记。
- 换人、登出、登录过期，这个人名下的全部作废。

**2. 一个实验服务器。** 公开数据集的环境太干净，缓存怎么用都不会错，测不出好坏。我们自己搭了一个银行加商店的服务器，可以按剧本安排别人改数据、登录失效、工具清单变化、请求或回复丢失。BFCL、τ²-bench、AppWorld 三个数据集也接到了它后面。

**3. 五批 case。** 64 条自建的，511 条从三个公开数据集改造的，从中抽的 12 条，一条长任务和一条双智能体任务，以及新做的四条。

## 旧规则和新规则

缓存拦下重复的调用，省的是请求。要省模型的思考，还得在模型做决定之前把已有的结果交给它。交什么，有两条规则。

| | 旧规则（设计稿 4.3） | 新规则（11 月 23 日加的） |
|---|---|---|
| 交什么 | 本轮读过、仍然有效的结果 | 仍然有效、但模型眼前没有的结果 |
| 本轮刚读过的 | 再说一遍 | 不重复 |
| 之前的轮次读过的 | 不交，模型只能再调用一次 | 直接把值交给模型 |
| 别的智能体读过的 | 不交 | 直接把值交给模型 |
| 省什么 | 请求 | 请求，加上模型调用轮数 |

旧规则交的是模型刚刚看过的东西，替代不了任何调用。模型真正要再调用的，是之前读过、现在看不到的值，这些正好在旧规则的范围之外。

## 结果

**脚本跑的**（按标准答案一步步调用，不是真实模型，用旧规则）：

| | 无缓存的请求数 | 加缓存的请求数 | 减少 |
|---|---|---|---|
| 自建 64 条 | 1052 | 751 | 29% |
| BFCL 138 条 | 2069 | 1395 | 33% |
| τ²-bench 228 条 | 4331 | 3809 | 12% |
| AppWorld 145 条 | 7770 | 7240 | 7% |

**真实模型，新做的四条**（Claude Haiku 5.5，每种设置 3 次，表里是平均）。前三条里有一部分轮次问的都是读过且没变的值，可以直接回答；第四条是对照，没有可复用的内容。

| case | 设置 | 请求数 | 模型调用轮数 | 输入令牌 | 用时 |
|---|---|---|---|---|---|
| 回访（10 轮，5 轮可直接回答） | 无缓存 | 52 | 25.7 | 36 万 | 257 秒 |
| | 旧规则 | 22 | 26.3 | 40 万 | 270 秒 |
| | 新规则 | 22 | 20.0 | 30 万 | 204 秒 |
| 多步查询（8 轮，3 轮可直接回答） | 无缓存 | 55 | 27.3 | 38 万 | 286 秒 |
| | 旧规则 | 21 | 28.0 | 43 万 | 283 秒 |
| | 新规则 | 20 | 19.3 | 29 万 | 197 秒 |
| 三智能体交接（10 轮，4 轮可直接回答） | 无缓存 | 46 | 29.3 | 43 万 | 295 秒 |
| | 旧规则 | 23 | 31.0 | 56 万 | 345 秒 |
| | 新规则 | 20 | 22.0 | 36 万 | 227 秒 |
| 对照（10 轮，0 轮可直接回答） | 无缓存 | 52 | 33.7 | 49 万 | 363 秒 |
| | 旧规则 | 38 | 33.3 | 54 万 | 346 秒 |
| | 新规则 | 36 | 28.7 | 43 万 | 311 秒 |

- 旧规则：请求少五到六成，轮数、令牌、用时都不降。
- 新规则：前三条的轮数少 22% 到 29%，令牌少 15% 到 24%，用时少 21% 到 31%。
- 对照那条新规则也少了 15% 的轮数，但无缓存的 3 次是 31、32、38 轮，新规则是 31、26、29 轮，差别在波动范围内。

**交接那条的答对数**（共 37 个值，3 次运行）。汇报智能体被问到余额时，另一个智能体已经转过账。

| | 标准说明 | 去掉“已有结果就不要重复调用”那句 |
|---|---|---|
| 无缓存 | 32、32、32 | 35、35、37 |
| 旧规则 | 28、32、32 | 32、32、37 |
| 新规则 | 37、37、37 | 37、37、37 |

无缓存和旧规则下，汇报智能体沿用了自己对话里的旧余额。新规则把另一个智能体刚读到的新值交给了它。去掉那句说明后错得少了，但没有消失。

**真实模型，公开数据集上的增广**。把回访和交接这两种结构加到了三个公开数据集的原任务后面，共 102 条，脚本检查全部通过。从中每个数据集取 2 个原任务、每种结构 1 条，共 12 条，每种设置跑 1 次。前四行是追加部分的模型调用轮数。

| | 无缓存 | 旧规则 | 新规则 |
|---|---|---|---|
| BFCL（4 条） | 36 | 33 | 26 |
| τ²-bench（4 条） | 47 | 47 | 39 |
| AppWorld（4 条） | 57 | 40 | 28 |
| 合计 | 140 | 120 | 93 |
| 整次运行的请求数 | 341 | 219 | 199 |
| 整次运行的输入令牌 | 899 万 | 873 万 | 723 万 |

- 新规则：追加部分的轮数少 34%，整次运行的令牌少 20%。旧规则只少了请求。
- τ²-bench 第一次跑没有收益：模型改用另一个工具查同一个值，那个工具返回的是易变数据，不能缓存。把提问换成只有慢变工具能查到的值后，轮数少 17%，表里是改后的数字。
- 这批数据暴露了我们方法的两个错，已经修了。一是写操作被拒之后，文件已经建好，缓存仍返回旧的拒绝。二是一次参数写错的调用被当成“失败操作”告诉了另一个智能体，它就不再调用这个工具了。

**真实模型，之前的三组**（新规则，长任务和双智能体是 3 次的平均）。这些任务里几乎没有可以直接回答的轮次，所以轮数基本不降。

| | 请求数 | 模型调用轮数 | 输入令牌 |
|---|---|---|---|
| 抽样 12 条 | 192 降到 135 | 191 降到 167 | 659 万降到 591 万 |
| 长任务 | 63 降到 32 | 35 降到 29 | 49 万降到 47 万 |
| 双智能体 | 37 降到 22 | 22 升到 23 | 32 万升到 38 万 |

## 缺陷

**1. 省模型的开销是有条件的。** 要用新规则，而且任务里要有可以直接回答的轮次。模型一轮会并行发好几个调用，少几个调用不会少一轮。这种轮次在真实任务里占多少，我们没有数据。

**2. 新规则不在设计稿里。** 设计稿 4.3 写的是旧规则，代码的默认配置也是旧规则。

**3. 正确性的优势只有一条 case。** 单个智能体时，真实模型没有缓存也不犯错。

**4. 契约写错，缓存就会答错。** 说明里写“余额只有自己会改”，实际别人存了钱，缓存就给出旧值。脚本实验里我们方法的失败全是这一类：自建 3 条，BFCL 11 条，τ²-bench 20 条，AppWorld 14 条。

**5. 公开数据集上的结果还很初步。** 增广的 102 条只抽了 12 条用真实模型跑，每种设置 1 次。τ²-bench 上收益最小；AppWorld 的原任务很长，脚本检查里整体请求只少 16%。

**6. 登录被服务器作废后，缓存仍会交出之前查到的值。** 52 条相关 case 里每条发生一次。服务器不通知 Host，要堵上只能每轮多发一个请求去确认。

**7. 令牌的数字不干净。** 我们用的命令行后端自己的开销占输入令牌的四成左右，而且是随机的。

**8. 实验太少。** 真实模型只跑了 30 条、一个模型，新做的四条每类只有 1 条，而且是知道原因之后专门设计的。那 64 条和 511 条还没用真实模型跑过。
